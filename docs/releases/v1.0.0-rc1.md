## PRIMERS OS 1.0 Genesis — release candidate 1

A pre-release for testing, **not** the final 1.0. Ubuntu 22.04 LTS base
(HWE kernel), Openbox desktop, PRIMERS Brain with Ask Primers, Primers Lite
Bee, Calamares installer (BIOS and UEFI, Secure Boot capable), Wine and
gaming tools, Data Saver, the campus modes (Lab Mode, Study Mode, Exam
Mode), primers-fleet for invigilators, Primers ID sign-in, and the privacy
notice with log retention.

> **For pilots and practice exams, not yet for a real exam.** Everything
> below is tested in virtual machines, including real Moodle and TCExam
> installations, but not yet on a physical lab PC, a campus's own CBT
> server or a real lab network. Before a real exam, run a full mock exam
> on the lab's own PCs and CBT server (pilot guide, sections 1–3).

### Tested

All in QEMU virtual machines (KVM on the release workflow's runner, on
this exact image); nothing in this RC has been run on physical hardware.
The release is only published if every check passes: 277 checks in 12
scenarios.

| Area | What was checked |
|---|---|
| Boot | Live USB boots to the desktop on legacy BIOS, UEFI, and UEFI with Secure Boot enforced (Microsoft keys); an unsigned bootloader is refused. |
| Install | The installer itself, driven through its screens: "Erase disk" on legacy BIOS and on UEFI with Secure Boot enforced. It refuses login names the system uses (`staff`, `lab`). The installed system boots with Secure Boot enforced, a locked-down kernel and the signed shim, has the administrator in `sudo`, its own machine id and no live-session tools. |
| Lab Mode | Live and installed (BIOS, UEFI with Secure Boot): the passwordless `lab` account is wiped at every sign-in, sign-out and boot, also after a restart with a student still signed in. |
| Exam Mode | Full-screen kiosk; the lab account reaches only the exam servers. Escape routes closed and checked live and on installed systems: text consoles, Ctrl+Alt+Backspace, Magic SysRq, Print Screen, clipboard, the clock, DNS (other servers, DNS over HTTPS, tunnelling), a shell, sudo, su, pkexec; a killed kiosk returns to the login screen; the boot menu is locked during an exam. ### Not tested yet, or known gaps

- **Physical hardware** of any kind, including Wi-Fi chips, 2G/LTE modems and printers.
- **Hard disk boot time misses its target** in the VM: power-on to login 73 s (target 30 s), kernel to login 32 s. Much of the time before the kernel is the emulated disk; real hard-disk PCs still need measuring. Plan in `docs/benchmarks.md`.
- **Firmware**: Exam Mode can't stop a candidate who boots something else. Set a firmware password and turn USB and network boot off on exam PCs (pilot guide, "Lock the firmware").
- **Exam machines must be installed**: the live USB keeps nothing across a restart and its boot menu can't be locked.
- **Installs not tested yet**: encrypted (LUKS), next to another system (dual boot), manual partitioning, and the installer's "Restart now" path.
- **A campus's own CBT server and a real lab network** (only self-hosted Moodle and TCExam on the test machine, and a virtual LAN for primers-fleet).
- **The live Primers ID service** isn't running yet; `primers-id login` says it can't be reached until it is.
- **Privacy text** is not legal advice: the institution's data protection officer should confirm it, and each PC needs `sudo primers-privacy controller` to name the institution.
- **The splash blinks at 1.0 s**, not the brand's 1.06 s: Plymouth's splash cycle is a fixed 2 s, which 1.06 s doesn't divide.
- The ISO is about 1.9 GB.

### Fixed before this RC

Images built on GitHub's runners gave the runner's user id (1001) ownership
of `/`, `/etc`, `/usr` and the files PRIMERS OS adds; on an installed PC
that id goes to the second account (often the Lab Mode account), which
would then be root in all but name. The build now installs every file as
root, and two gates refuse an image with such owners. No image with this
fault was published.

The installer couldn't install on UEFI PCs with "Erase disk" (Calamares
3.2.61 sizes the root partition over GPT's backup table); a small
correction in the live session fixes it. It also accepted `staff` as the
administrator's login name, which then failed at the very end; it now
refuses names the system uses.
